# Charge-Limit-for-Honor
一个基于KernelSU为荣耀MagicOS10开发的自定义充电上限模块
> 设备：HONOR PTP-AN00 (Magic7) / Android 16 / KernelSU root
> 形态：**标准 KernelSU 模块**（可在 KernelSU 管理器模块列表中查看/启停/卸载）
> 
## 适用机型与环境要求
- **机型专用**：本模块读写的是**荣耀专有内核节点** `/sys/class/hw_power/soc_control/control`
  （由厂商自带的内核模块 `honor_soc_control` 提供，非本模块加载）。
  - 已知适用：**HONOR Magic7 (PTP-AN00)**；其它使用 `honor_soc_control` 的荣耀机型（同为 Magic 系列 / 同代平台）可尝试。
  - **非荣耀机型或不含该节点的系统上会静默失效**（写节点失败，守护只在日志里记录，不会造成任何损坏）。
  - 自查命令：`su -c 'cat /sys/class/hw_power/soc_control/control'` —— 能读到 `enable=…` 即为支持。
- **环境要求**：
  - 已 **root**，且使用 **KernelSU**
  - **无系统改动**：模块不覆盖任何系统文件，卸载即恢复；`uninstall.sh` 会把节点重置为「不限制」。

## 模块结构
```
/data/adb/modules/charge80/
├── module.prop        # 模块信息（名称/版本/说明）
├── service.sh         # 开机自启（KernelSU late_start，拉起守护）
├── uninstall.sh       # 卸载时停守护 + 解除限制
├── webroot/
│   └── index.html     # 图形界面（KernelSU 模块 WebUI）
└── bin/
    ├── charge80.sh    # 常驻守护（每 30s 轮询，按状态写内核节点）
    └── charge80ctl    # 控制脚本
```
运行数据（不属于模块，卸载后保留）：`/data/adb/charge80/charge80.log` 等。

## 图形界面（WebUI）
模块内置 KernelSU 模块 WebUI：在 **KernelSU 管理器 → 模块 → Charge Limit (Magic7)** 里，
模块会显示一个可点击的图形入口（与 Zygisk Next 的界面同机制），点进去即可：

- 查看当前上限 / 电量 / 内核节点状态
- 拖动滑块设置上限（5%–100%）并「应用上限」
- 一键「恢复限制 / 一次性充满 / 启用 / 停用」
- 底部日志显示命令输出

> 首次部署后若管理器没刷新出入口，退出重进管理器（或重启一次管理器）即可。

### 五种模式语义
- **hold（默认）**：保持充电上限。
- **release（临时恢复）**：写 `release` 标记 → 内核关上限放行充满；
- **off / on**：永久停用 / 启用（off 状态跨重启保持，直到 on）。

## 性能与耗电

**本模块不加载任何内核驱动**：
`honor_soc_control`（16384 字节）是**荣耀厂商自带**的内核模块（由`honor_charger_adsp` 持有），
本模块只是往厂商本来就存在的节点里写一行字符串；内核侧开销仅为充电驱动里多一次数值比较，可忽略。

实测开销：
| 项目 | 实测值 |
|---|---|
| 常驻内存 | RSS ≈ 2 MB |
| 累计 CPU | ≈ 1 秒 / 小时（单核 ≈0.03%，整机 8 核折算 ≈0.004%） |
| 轮询间隔 | 30 秒（约 120 次唤醒 / 小时） |
| 写内核节点 | 仅在配置变化或节点与意图不符时才写，稳态不反复写 |
| 日志体积 | 约 8 KB / 9 小时，仅在电量变化时写一行 |
| 网络 / wakelock | 无 |

结论：
- **性能影响可忽略**：唯一的理论影响是每 30 秒一次、毫秒级的调度抖动，无可感知卡顿。
- **耗电增加很小**，约 **0.2%–0.6% / 天**：主要来自“每 30 秒把 CPU 从深眠唤醒一次”，
  而非 CPU 时间（CPU 时间每小时仅约 1 秒），远低于微信 / QQ 等后台推送。
- **附带收益**：充电长期停在设定上限（如 88%）可减少锂电池高电量搁置的损耗与发热。

### 轮询间隔带来的延迟（正常现象）
守护是「定时轮询」而非「事件实时」的，因此下列动作最坏会晚一个轮询周期（≤30 秒）才落地：

- **点按「一次性充满」后**：该操作只写一个标记文件，真正的放开限制由守护下一轮完成。
  因此期间内核节点仍为 `enable=1`，界面「校验」行会**短暂显示“不一致”**，
  最长约 30 秒后自动变为“一致”。**这是设计内的过渡态，不是故障。**
- 「一次性充满」的自动恢复（充满到 100% 或拔线后）同样最多晚 30 秒。

而 **`set`（改上限）/ `hold` / `on` / `off` 不受影响**：这些操作由 `charge80ctl` **直接写内核节点**，即时生效。
